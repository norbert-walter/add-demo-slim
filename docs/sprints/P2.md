## Aufgabe P2.4 – /add.html blockweise, BAD_PARAM bei GET_STATE/GET_CONFIG (Contract V1.5.17)

Review von P2.1–P2.3: alle 26 Tests grün, `firmware-partial` erfolgreich, `wifi_manager` im
Differenztest (40 × 20 000 Schritte) identisch. Drei Befunde, zwei davon in `http_server.cpp`:
`/add.html` schickt jedes Zeichen als eigenen Chunk (auf dem Gerät eine TCP-Schreiboperation pro
Byte) und verliert ein `<` am Dateiende; `BAD_PARAM` bei GET_STATE/GET_CONFIG wird als OK
beantwortet (Differenztest). Prompt mit Diagnose, ohne Code-Zeilen.

```
Sprint P2, task 4. Branch: work-p2. Two new frozen tests fail (Contract V1.5.17):
test_v1517_add_html_sends_blocks_not_bytes and
test_v1517_bad_param_is_an_error_also_for_get_state_and_get_config (test_http_server).

Rules: change ONLY sendScriptJson, sendHtmlEscaped and handleApi in src/comm/http_server.cpp.
Allowed reads: these three functions; the V1.5.17 lines in src/comm/http_server.h
(grep -n "V1.5.17" -A4 src/comm/http_server.h); the two test functions named above
(grep -n "void <name>" and read only that function). Do not modify tests, shims or headers.
Do not commit. Report results only by copying tool lines.

Diagnosis (already done):
1. sendScriptJson and sendHtmlEscaped call server.sendContent once per character (a one-char
   String each time). On the device every sendContent is one HTTP chunk and one TCP write:
   about 8000 writes for a 4 kB file. The header (V1.5.17) requires block-wise sending:
   collect the output of one read block in a local char array (big enough for the worst case,
   e.g. every byte escaped to 5 chars) and send it with ONE sendContent per block.
   Keep the 64-byte read buffer or use 256 bytes; both stay within the limit.
2. sendScriptJson holds back a '<' at the end of a block (correct) but never sends it when the
   file ends: after the read loop, a still pending '<' must be sent.
3. handleApi checks GET_STATE / GET_CONFIG before it checks the parse result. With a valid
   packet that has bad params ("params":[1]) apiParseRequest returns BAD_PARAM with cmd.id =
   GET_STATE; the code then answers the state with OK. Every result other than OK (BAD_PARAM
   included) must be answered as an error first (heartbeat stays as it is); GET_STATE /
   GET_CONFIG / queue only for OK.

Run: pio test -e native -f native/test_http_server, then pio test -e native (all green),
then pio run -e firmware-partial -s; echo "exit $?"   (must be exit 0).
Done when: test_http_server 19/19, frozen check clean.
Report: the SUMMARY lines verbatim and the exit line.
```

Diagnosis (already done): wifiLoop calls WiFi.status() and staStep() between

log lines, timing variables) stays as it is.
